# 小白版：为什么语音转写会"冻住"手机屏幕，以及我们怎么治好它

> 正常技术版：@postmortem-recognition-worker-isolate.md · 2026-08-27

## 先说结论

以前：说 1 分钟的话，转写的时候整个 App 会**冻住 5 秒**——按钮点不动、动画停了、像个死机。
现在：转写在"后台小房间"里干，屏幕**全程顺滑**。悬浮窗里也能直接录音转写了（像锤子的闪念胶囊）。

## 到底为什么会冻住？——一个餐厅的故事

把 App 想成一家**只有一个服务员的餐厅**：

```
┌───────────────────────────────┐
│  餐厅（App）                    │
│                               │
│  服务员小明（主线程）            │
│  ┌─────────────────────────┐  │
│  │ 接待点单（响应你的点击）      │  │
│  │ 端盘上菜（刷新屏幕动画）      │  │
│  │ 炒菜（语音转写！）           │  │
│  └─────────────────────────┘  │
└───────────────────────────────┘
```

这个服务员身兼三职。平时菜少（10 秒语音）没问题；但你说了一段 **1 分钟的话**，他就得钻进厨房炒 5 秒钟的"大菜"——

```
炒菜期间：
- 你点单？听不见 ❌（点不动按钮）
- 别桌要上菜？没空 ❌（动画卡住）

= 屏幕冻住 5 秒
```

**"冻住"不是坏了，是唯一的服务员在忙别的事。**

## 那加个"await"不就行了？——为什么之前的办法都没用

### 尝试 1：跟小明说"你先答应一声再去炒菜"（async/await）

```
小明："好嘞收到~"（屏幕亮了一下）
小明钻进厨房炒菜 5 秒
餐厅照样没人管 ❌
```

`await` 和 `Future` 只是让小明**嘴上应一声**，但他还是同一个人。菜还得他炒，炒的时候餐厅还是停摆。**这叫"假异步"**——看起来是后台，其实还是前台。

### 尝试 2：雇个帮厨，让他把"锅"交给小明（2026 年 1 月的 Isolate 尝试）

当时的想法：找个帮厨（子线程）先把菜炒好。但代码上犯了个错——让帮厨把他手里的**锅**（识别器对象）递给小明继续用。

```
帮厨："锅给你！"
小明："我接不住啊！" 💥
（锅 = FFI 指针，不能跨线程传递）
```

接不住怎么办？小明只好**自己去买口新锅、重新开火**——等于又从头炒一遍，白忙。于是当时得出结论：

> "在 Flutter/Dart 层面无法真正解决这个问题"

然后退而求其次：**让服务员先把欢迎仪式演完，再去炒菜**（先播 1.5 秒动画再转写）、**把 1 分钟的大菜切成 6 道 10 秒的小菜**（VAD 分段，一次卡 1 秒总比卡 5 秒强）。这些"遮掩"手段一直用到现在。

### 关键误会在哪？

"帮厨递不出锅"是真的，**但结论错了**。正确用法根本不需要递锅：

```
✅ 正确：锅永远留在厨房，递食材和菜
❌ 错误：递锅本身
```

## 现在的解法：厨师长住厨房

2026-08-27 的改造就一句话：**给餐厅配一个专职厨师，他带着自己的锅常住厨房，永不离开。**

```
┌─────────────────────────────────────────────┐
│  餐厅（App）                                  │
│                                             │
│  服务员小明（主线程）        厨房（worker 线程） │
│  ┌──────────────┐          ┌──────────────┐ │
│  │ 接待点单 ✅    │  递食材    │ 厨师（专职）    │ │
│  │ 端盘上菜 ✅    │ ────────▶ │ 锅（识别器）    │ │
│  │              │  (语音数据) │ 炒菜（转写）    │ │
│  │              │ ◀──────── │              │ │
│  │              │  端出成品   │ 炒好装盘        │ │
│  └──────────────┘  (文字)    └──────────────┘ │
└─────────────────────────────────────────────┘
```

- 小明把**食材**（录下来的声音数据）从窗口递进厨房——食材是普通东西，可以递
- 厨师炒好，把**成品**（识别出的文字）从窗口递出来——文字也可以递
- **锅（识别器）从头到尾不出厨房**——谁也不用接锅了

厨师炒 5 秒菜，小明该干嘛干嘛——你的屏幕从此不冻。

> 技术对照：厨房 = 常驻 worker isolate；食材 = Float32List PCM 数据；成品 = String 文本；锅 = FFI 指针对象（不可跨 isolate）。Dart 的每个 isolate 天生跑在独立线程上，这功能 2026 年 1 月就有，只是当时用错了姿势。

## 这次还顺手做了什么：悬浮窗里的"闪念胶囊"

像锤子手机那样：**长按音量上键 → 悬浮窗蹦出来直接录音**，小胶囊随说话时间慢慢变长，再长按一下结束，转写完自动变成一条胶囊卡片挂进列表。

### "万一厨师也卡死了，悬浮窗挡住整个屏幕怎么办？"

这是整个方案里最 scary 的担心。答案：**移除悬浮窗的开关在安卓系统手里，不在厨师手里。**

```
悬浮窗的"关闭"走的是另一条电路：
  长按音量键 ──▶ 安卓系统直接摘掉悬浮窗 ✅
                （完全不经过厨师/Flutter）
```

就算厨房彻底冒烟（Dart 卡死），长按音量上键也能立刻把悬浮窗摘掉，桌面恢复正常。另外还有一套"保安巡逻"（四级 watchdog）：60 秒没动静就自动叫停、66 秒强拆悬浮窗、76 秒把整个厨房炸掉释放麦克风——最坏情况也有底线。

## 一句话教训

> **失败的时候，记下"哪种姿势失败了"，别急着说"这件事做不成"。**
> 当年"递锅失败"被记成了"厨房方案不行"，这个误会挡了我们 7 个月。
